Summary

Extracted shared logic for multi-property template processing into a reusable base class: BaseMultiplePropertyOrchestrator<TContext>.

This consolidates common orchestration behaviour across implementations and reduces duplication.

What was done
Introduced BaseMultiplePropertyOrchestrator<TContext> to encapsulate shared workflow:
Template validation
Row extraction
Context building
Property limit construction
Geolocation processing
Prior submit evaluation
Upload result construction
Defined clear extension points via abstract methods:
ValidateTemplateColumns
ExtractLocationRows
ExtractContextAsync
BuildPropertyLimitsAsync
BuildUploadResult
InsertPropertyLimitsIntoWorkbook
Centralised cross-cutting concerns:
Address validation (HasInvalidLocationValidationAsync)
Duplicate detection (IdentifyDuplicateAddressKeys, HasDuplicateAddress)
Geolocation enrichment and reconciliation
Client location matching and reuse
Country/state resolution
Standardised the orchestration flow in GetPropertyLimitsAsync:
Validate template
Extract rows + context
Build property limits
Enrich with geolocation
Run prior submit checks
Build final result
Why this change

Previously, orchestration logic was duplicated and tightly coupled within individual implementations. This made it:

harder to maintain
error-prone when introducing new features (e.g. geolocation, prior submit)
difficult to ensure consistent behaviour across products

This refactor:

enforces a consistent processing pipeline
improves separation of concerns
makes adding new product-specific orchestrators simpler and safer
reduces duplication and future maintenance overhead
Impact
Existing orchestrators now inherit from the base class
No functional changes intended to business behaviour
Improved extensibility for future property template types
Notes
The base class is marked internal and designed for extension within the integration layer
Product-specific logic remains isolated via overrides
Unit tests added/updated to cover shared behaviours
